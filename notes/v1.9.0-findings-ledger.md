# v1.9.0 findings ledger — what the v1.8.0 cycle taught, as work

Draft for master-release. Nothing here is filed. Every count carries the
command or the `file:line` that produced it, because the single most
common defect this cycle was **a count of the wrong thing, which looks
exactly like a real count**.

Measured against `origin/dev` @ `e410107`.

---

## 1. The phantom zero, as one class rather than eight anecdotes

**The mechanism: the measurement never ran, and nothing said so.** Every
instance arrives as a confident number — usually zero — produced by an
instrument that could not have seen the thing it was reporting the
absence of.

Eight instances, four people, one working day:

| # | instrument | what it actually measured |
|---|---|---|
| 1 | `sed` substitution in a mutation script | matched nothing; the "mutant" was the original |
| 2 | `command -v` inventory of `$PATH` binaries | found one of two; the other reached `execve` through a shell (#707 → #761) |
| 3 | 17 test fixtures in `orphan_sweep_test.go` | both sides of the comparison were the same constant, so they moved in step (#722 → #765) |
| 4 | `grep -c '^--- FAIL'` after a mutation | the mutation did not compile; zero failures over zero tests |
| 5 | a host-specific gate run off its host | oversight, on a gate whose evidence only exists on the arm64 board. **Not a gate-design defect** — a claim that two gates fail rather than refuse was checked and withdrawn (see below) |
| 6 | `grep -r <snake_case_counter> --include='*_test.go'` | tests name the Go atomic, not the exposition string. Reported `network_options_rejected` as untested; it has **10 assertion lines** in `stored_options_names_test.go` |
| 7 | lowerCamel derivation from a Go field name | produced `dHCPRoutesApplied`; Go spells it `dhcpRoutesApplied`. Four more false zeros |
| 8 | `test -x a b c` in the Dockerfile | busybox `sh` rejects the three-operand form, rc=2 **whatever the files are** — see item 11 |

Instances 6 and 7 happened **while writing this ledger**, twenty minutes
apart, verifying item 5's sibling claim. They are the reason this is one
item and not a footnote: the class does not stay caught.

**Two controls, and the second is the one that keeps getting skipped.**

1. **Verify the substitution landed** before trusting the run. `grep -q`
   the mutated line back out of the file and abort if it is absent.
2. **Verify the measurement ran where it was meant to run.** A build
   failure, a wrong host, a wrong tree, a wrong ref and a wrong regex are
   the same defect. Surface them explicitly rather than letting them
   fall through a counter.

A third, learned from 6 and 7: **derive names from the declaration, not
from a rule.** `obs3.sh` reads the atomics out of `plugin.go`'s own
struct and **refuses to report if it finds fewer than 30** — which is
what finally produced a true answer.

**That floor was invented three times on 2026-08-22, independently, from
three directions**, which is the argument for making it a gate rather
than a habit:

1. client1, inside a test: *a loop-based test must count what it
   inspected and fail on too few*, or a render that produced nothing
   passes the loop by reading nothing.
2. this ledger's counter measurement: refuse to report unless at least
   30 atomics come back from `plugin.go`.
3. the release-notes claim sweep: refuse to report a clean sweep unless
   at least 200 added lines were extracted — because an empty added-set
   greps clean, and that is indistinguishable from finding nothing
   wrong.

**The gate shape:** any check that iterates over a discovered set must
emit the size of that set and fail below a floor.

Measured rather than guessed — the first draft of this paragraph named
three gates from memory and one of them does not carry the refusal at
all, which would have been instance 9:

```
$ grep -rlc 'Nothing to inspect' scripts/check-*.sh | wc -l
8
$ ls scripts/check-*.sh | wc -l
56
```

**Eight of fifty-six.** (Item 16 is the designed form of the gate; this
is the size of the ground it has to cover.) The eight are `check-lane-hygiene.sh`,
`check-openat-cloexec.sh`, `check-pipefail-consumers.sh`,
`check-allowlist-parity.sh`, `check-dispatch-reachable.sh`,
`check-coverage-floor.sh`, `check-concurrency-parity.sh` and
`check-python-deps.sh` — most of them because #734 or #743 put it there
this cycle, not because it was house style. That is the size of the
work: the rule is that "found nothing wrong" and "inspected nothing"
must never print the same line, and forty-eight gates can still print
it.

(Eight is a lower bound on gates that refuse *somehow* — it counts that
exact string, which is the convention #734 established. A gate refusing
in its own words would not be caught by this grep, and finding those is
part of the work rather than a reason to distrust the eight.)

### Instance 5, and a claim withdrawn rather than written up

The host-specific-gate instance was nearly promoted to a standalone item
— *"two gates fail rather than refuse when run off their machine"* — and
it does not survive checking. Recorded because the checking is the
useful part:

- Only two gates in the corpus lack an `exit 2` path at all:
  `check-release-tooling.sh` and `check-manifest-parity.sh`.
- `check-release-tooling.sh` exits 1 when `gh`, `cosign` or a signing key
  is absent, and that is **correct by design** — it is a pre-flight
  asking "can I run the runbook from this box", where "cannot check" is
  the wrong answer. It is not a lane member.
- `check-manifest-parity.sh` reads the tree, not the host; its exit 1 is
  a drift verdict.
- `check-host-watchdog.sh:84-86` and `check-pi-watchdog-wiring.sh:58,69`
  both refuse correctly with `exit 2`, documented in their own headers.

So there is no such pair, and what was being remembered is instance 5
above. **Twelve items that are all true beats thirteen with one that
cannot be sourced** — which is the same standard the rest of this
document is written to.

**The work:** the mutation-testing recipe in the runbook currently
describes the technique and not the controls. It should carry both, plus
a worked example of a mutation that does not compile.

## 2. A comment claiming coverage is itself a counted claim

Three instances this cycle, and the direction the runbook misses is not
a claim going stale — it is a claim that **was never true**:

- **#707's constant comment** said `unshare` was *"the one binary in the
  tree whose identity depends on an environment variable."* `dhcpcd` sat
  one argv position to the right in the same command line. The sentence
  is what made the gap durable: a surface declared clear does not get
  re-checked. Fixed in #761 by correcting the comment **in place**, so
  the next reader gets the method that produced the gap rather than a
  new conclusion.
- **`orphan_sweep_comm_test.go`, twice, by me** — in the very file
  written to demonstrate the principle. The first draft claimed
  `ComparandIsAComm` pinned the comparand; measured, a body revert
  reddens nine tests and a call-site revert reddens eight, and that test
  is the one missing from the second set. Narrowed to name what it pins
  *and what it misses*.
- **`check-dispatch-reachable.sh`'s** header promised block or inline
  `on:`; the pattern matched only the block form (#743).
- **My own release-notes draft, on my own second pass** — and this is
  the instance worth keeping, because it is the rule demonstrated on the
  person who had just been asked to apply it. The draft asserted
  *"Option 3 was the one path into the gateway that was not validated on
  the way in."* Same sentence shape as #707's, written by someone who
  had spent the afternoon writing up why #707's sentence was the defect.
  It happens to be true — there are exactly two writes into the lease
  gateway from the wire, `pkg/dhcp/event_builder.go:313` and `:315` —
  and it was caught not by knowing better but by a mechanical sweep for
  completeness phrasing over my own added lines. **Applying the rule
  once is not applying the rule.** client1 applied it twice to #730 and
  oversight still found a third stale copy in `docs/internals.md`
  afterwards.

**The work:** a claim about what a check covers should be verifiable the
way a count is. Where a comment says "this catches X", the cheapest
control is to have actually reverted X and recorded the number of reds
in the comment — which is what the two surviving comments in
`orphan_sweep_comm_test.go` now do.

## 3. A gate that no workflow runs is invisible to every rule that starts
from the workflows

`check-local-lane.sh`'s rules 1–3 all begin from what `test.yaml`
invokes, so a gate script nothing invokes could not be seen by any of
them. Rule 4 (added in #763) closes that direction by starting from the
scripts on disk instead.

Reproduced against a tree built from `origin/dev`'s workflows + scripts
at the time: **one** orphan, `check-fuzz-budget.sh`. On the merged tree:

```
PASS  local lane covers 46 script(s) from .github/workflows/test.yaml:
      41 run, 5 declared out of lane; 56 check-*.sh on disk, none orphaned
```

**The work is the generalisation, not the gate.** Every reconciler in
`scripts/` has a direction it does not look. The question worth asking of
each is not "does it fire" but **"what would it be unable to see?"** —
which is the same question that produced #743, #758 and rule 4.

## 4. A mirror test cannot catch a change to the thing it mirrors

`SweepOrphans` compared `/proc/<pid>/comm` against `dhcpcdBin`. When
#761 made that constant absolute, the comparison became one that can
never be true — and **seventeen fixtures agreed with it**, because they
spelled the same constant on both sides. Making it absolute moved both
sides in step and the suite stayed green. The sweep ran on every boot,
found nothing, and reported that confidently.

Fixed in #765: the fixtures now spell out what the kernel would actually
have written (`realKernelComm = "dhcpcd"`), and
`TestComm_IsAlwaysABasename` starts a real process by absolute path and
reads the kernel's own `/proc/<pid>/comm` back — so the premise is
verified against the kernel rather than restated in a comment.

**The work:** a rule for fixtures. *A fixture must not be derived from
the value under test.* Where one side of a comparison comes from outside
the process — the kernel, the engine, the wire — the fixture has to
spell out what that outside would produce, in its own literal. This is
gate-able by inspection: a fixture referencing a production constant in
a position that constant is compared *against* is the shape.

## 5. An artifact that proves a counter renders is not an observer of the
counter

`pkg/plugin/testdata/metrics_exposition.golden` pins every counter's
**name, help text and rendering**. It establishes nothing about whether
anything ever increments one, and it would stay green with an increment
site deleted. That is the `SweepOrphans` shape (item 4) one level up,
and it generalises to all forty-nine atomics on `Plugin`.

**The instance that produced this is fixed, not deferred.**
`dns_propagation_pid_mismatches` and `netns_pid_mismatches` had *no*
observer beyond the golden file — increment sites at
`dhcp_manager.go:784` and `:1433`, nothing asserting either. As of
`26784cf` on `fix/707-mountprep-shell-binaries` (unmerged at the time of
writing) the two call sites are extracted to one `notePIDMismatch` and
`dhcp_values_test.go:777`/`:780` assert both across six subtests, four
mutants dying to four different subsets. It ships in v1.8.0 and is
written up in the release notes.

**What stays here is the question**, which nothing currently asks of any
counter: *what, other than the golden file, would go red if this counter
stopped counting?* For most of the forty-nine the answer is a test; the
two above were the ones where it was nothing, and they were found by
looking rather than by a check.

**The shape a counter should reach** is `network_options_rejected`'s:
`stored_options_names_test.go` asserts it **moves** on the refusal and
**stays zero** on the path that refuses nothing — `DeleteEndpoint`
deliberately not reporting a refusal it did not make. Both directions,
because a one-direction assertion stays green for a patch that deletes
the increment.

**The work:** this is gate-able. A counter declared on `Plugin` with an
`Add(1)` site and no `_test.go` naming it is a mechanical query — the
derivation in item 1's third control is most of the implementation.
Counters observed only through the integration suite
(`dhcp_server_tier_fallbacks`, `dhcp_server_policy_exhausted`, via
`test/integration/dhcp_server_policy_test.go:308-394`) must count as
observed, or the gate reports twelve false positives on its first run.

## 6. `childLinkUpBudget` is a fixed 3s against a measured median in the
hundreds of milliseconds

`parent_attached.go:165`, and its own comment at `:157-164` states the
premise: *"The thing being waited for is Docker completing a
DeleteEndpoint it has already begun, which is hundreds of
milliseconds."*

master-release's measurement, from today's runs: two `dev` reds, with
successes in the **same runs** at 1.7ms, 549ms and 614ms. So the budget
is not sized to the distribution's centre — it is sized to a tail that
the same run also crosses. The #307 comparison belongs on this item.

The constant is read at three sites: `orphan_release.go:233`,
`parent_attached.go:258` (log field) and `:401`.

**The work:** decide whether this is a budget that should scale, or a
retry that should be paced differently (`childLinkUpInterval` is
150ms, `parent_attached.go:169`), and whether a timeout here should
count. It currently surfaces as the plugin's own error, which is the
right direction — but nothing distinguishes "waited 2.9s and succeeded"
from "succeeded immediately" in the counters.

## 7. Nothing evaluates a merge product *before* it becomes `dev`

Scoped precisely, because the obvious remedy is already built and
proposing it would be wrong.

**The repo does have a merge-product check: the `dev`-push integration
run.** `scripts/integration-run-gate.sh push <treesha>` skips only when
a squash merge produces a tree **byte-identical** to one that already
passed, and its own comment names the case it refuses to skip — *"A tree
that differs — the semantic-conflict case dev-push runs exist for —
always runs."* For #757/#761 the base moved in between, so #761's merge
product was a different tree and integration **ran in full** on
`48365c4`, not a skip.

So the gap is the **before/after window**, and its cost is a red `dev`
for a few minutes rather than a blocked PR. Real, and small.

**What actually failed was observation, not sequencing.** `48365c4`'s
full run came back green — not because it ran too late, but because the
test was blind: the sweep tests run directly at `48365c4` return
`ok, 0.005s`. A merge-product gate placed before the merge would have
been just as green. Item 4 is the fix; this item is the smaller,
honest remainder.

**Two things about that gate worth keeping, because they are good design
nobody will notice:**

- It is **fail-open by design** — an API error, a missing tool or an
  unknown mode all print `run`. The expensive path is the safe one. That
  is the opposite of the `exit 2` refusal discipline everywhere else in
  `scripts/`, and it is right *here*, because guessing wrong costs a
  wasted run rather than a false green. The two disciplines should be
  written down together, since the difference is what the failure of a
  wrong guess costs.
- It is a **job step, not a workflow `paths:` filter**, precisely because
  `integration` is a required check and a workflow that never triggers
  leaves a PR stuck on "Expected" forever. That is the absent-vs-failed
  distinction, solved in the repo months before it bit two of us in
  verdict scripts today.

## 10. A gate that parses a file is not an observer of what the file does

**Reported by master-release, from the last hour, and already half-fixed.
It goes in as the general rule, not as an open item.**

A `test -x /sbin/dhcpcd /bin/mount /bin/mkdir` was added to the
Dockerfile to assert the two newly-pinned absolute paths. That line is
not a shorthand for three checks. On busybox `sh` it is
`sh: /bin/mount: unknown operand`, **rc=2 whatever the files are** —
measured on the pinned digest with all three present and executable.
Corrected to three chained `test -x`, and measured in both directions:
present rc=0, one missing rc=1, and the broken form fails the build with
all three present.

**The finding is not the typo.** The local lane reported
**50 passed, 0 failed** over a Dockerfile that could not build. Several
gates *read* that file — `TestDhcpcdBinMatchesDockerfile` parses the
binary path back out of it and was green — and **reading a line is not
running it.** The observer count for Dockerfile *execution* in the local
lane was zero.

**CI was not blind, and the item must say so** rather than implying a
hole that is not there: `reproducible-build.yml` and `trivy.yml` both
fire on a Dockerfile path change, and integration builds the image, so
this would have been caught at PR time. What was missing was the lane
telling its user that it had not run one.

Already fixed: `scripts/local-lane.sh` now carries a `NOT BUILT`
refusal block naming those three catchers, in the same spirit as its
untracked-files refusal.

**The general rule, which is the work:** *a lane must declare which files
it reads and never executes.* Every parse-only gate is a claim about a
file's contents, not about its behaviour, and the difference is
invisible in a green summary. This is item 1's shape at the file level:
the measurement never ran, and nothing said so.

## 11. One waiver spelling for three different meanings

**Reported by client1, who is the negative example in it. It is a gate
change and wants its own review — not #730's business.**

`scripts/check-test-weakening.sh` has one escape hatch,
`Test-weakening: #N`, and its own prose names one reason for it: *"if
the harness really is at fault."* A net assertion drop can mean at least
three different things, and after the fact the gate cannot tell them
apart:

1. **The harness was at fault** — the test was wrong. What the trailer
   is written for.
2. **The subject was retired** — the property became unrepresentable, so
   no successor is possible. Wants its own spelling, e.g.
   `Test-retired: #N`, with the body **required** to name the successor
   or to state that none can exist.
3. **The assertion was re-expressible and simply had not been
   re-expressed yet.** This should not be waivable at all. It is a
   review finding, and the gate found it correctly.

**#766 was an instance of case 3, and the waiver was reached for first.**
The gate flagged a net drop of one assertion:
`TestMetrics_FamilySplitClampsRatherThanEmitNegative` had been deleted on
the reasoning that its subject was gone. Half of it was — nothing can
make an aggregate counter read below its sibling once the v4 share is
stored rather than derived. But that test pinned **two** properties, and
the other one — *no rendered counter may be negative* — was still alive.
Deleting it was a real loss of coverage dressed as a tidy-up, and a
waiver would have made it permanent and unreviewable.
`TestMetrics_NoSeriesRendersNegative` now carries it: mutating the
renderer back to a subtraction makes it emit
`net_dhcp_leases_obtained_total{family="ipv4"} -4` and fail.

**The risk of one spelling for three meanings** is that case 3 gets
waived by whoever is in a hurry, and `Test-weakening:` stops
distinguishing a **deleted** observer from a **retired** one — which is
the failure the gate exists to prevent, one level up.

**Two habits worth carrying out of it**, and they generalise past this
gate:

- **Assert over the rendered surface, not over one series.** A future
  counter then inherits the promise without anyone remembering to extend
  the test.
- **A loop-based test must count what it inspected and fail on too few.**
  Otherwise a render that produced nothing passes the loop by reading
  nothing — and that false green is indistinguishable from a real one.
  This is item 1 again, inside a test rather than inside a script.

## 12. Search for the claim in words, not for the symbol

**Reported by client1 while fixing #730, and it is the transferable half
of that work.**

A rename pass reaches identifiers — including the ones inside doc
comments, which then *look* updated — and leaves prose asserting the old
design untouched. #730 removes the derived `family="ipv4"` series, and
`RELEASE_NOTES.md`'s v1.8.0 section still told operators the opposite, in
the notes for the release that removes the mechanism.

What found it:

```
grep -rn -iE 'aggregate minus|minus the matching|stay aggregates|derived, not stored|total - v6|total minus' \
  --include=*.go --include=*.md --include=*.sh --include=*.yaml --include=*.yml .
```

Five hits. Two live and false, one already correct, and **one that must
be left alone**: the v1.2.0 section says the same thing and it was true
then. *Historical sections are history; the unreleased section is a
promise.* A sweep that does not draw that line makes the changelog lie
about the past instead of about the present.

**And the sweep was declared done at two copies, and there were three.**
client1 asked for this to be said plainly, and it is the whole rule:
`docs/internals.md:365` was the third, and the worst of them — a
**present-tense heading**, *"The `ipv4` series is derived, never read"*,
stating the opposite of the PR title, in a teaching document, with no
diff drawing attention to it because nothing else in that PR touched the
file. It was found by a reader, after the author's own grep rule had
been applied and the sweep called complete.

**One pass is not the rule. The rule is that one pass is not enough** —
demonstrated three times in an afternoon, on three different people, two
of whom had just written the rule down.

**The work:** this belongs in the release runbook beside the
docs-vs-reality audit, as a step with its own grep — the audit currently
reads docs against code, and this is the case where the code and the
identifiers agree with each other and the sentences do not.

## 13. A verdict is about a SHA, not about a pull request

**Added after the twelve were agreed; cut it if you would rather keep
the list at twelve.** It is sourced — two instances on 2026-08-22 —
and it is a different mechanism from item 1, so it did not fold in
anywhere.

A review pass, a green check and a merge verdict are all statements
about a **tree**, and every one of them is delivered against a **pull
request**, which is a moving target. When the head moves underneath one,
the verdict does not become invalid-looking. It becomes
**indistinguishable from a valid one**.

Two instances, same day:

- client1 force-pushed #766 while it was with oversight; their first
  read was of a head that no longer existed.
- I pushed two commits to #768 while it was with oversight, from edits
  queued before the freeze existed. Both commits were correct and one
  had been requested. It still cost a pass.

Neither was carelessness, which is the point: **the pipeline had no
place to put the fact that a head had moved.** The same shape appears
three more times in this repo's recent history — an absent check read as
a green one, a merged PR's green history reverting to red when its body
was edited, and a nonexistent SHA read as STALLED.

Item 14 is the same lesson reached from the tooling side — *resolve,
never transcribe* — and rule 6a is where the two meet.

Already fixed in process, and recorded here because the process is not
in the tree: a CLEAR must name its SHA and is refused if that SHA is not
the current head, and a PR's head is frozen once it is with a reviewer.

**The work, if any:** these are conventions between sessions, not
anything the repo enforces. Whether they should be — a check that a
review verdict names the head it was issued against — is a real
question, and the honest answer may be no, since the reviewer is a
person and the freeze is social. It is written down so the next stale
verdict is recognised as a class rather than as an accident.

## 14. A gate that judges a moving external system is a different object
from a gate that judges the tree

**client2's item, in their words, because the mistake it rests on is
theirs and is load-bearing to the argument.**

Every gate in `scripts/` judges the tree: same input, same answer,
forever. If it says red, the tree is red, and re-running it tomorrow says
red again. **That property is what makes it safe to block a merge on.**

The CI verdict tool does not have that property. It judges GitHub through
an API that lies in specific, enumerable ways:

- `gh api --jq` writes a 4xx **error body to stdout**, so a failed call
  looks like a successful one to any emptiness check;
- the runs endpoint reports **zero for "nothing yet" and zero for
  "nothing ever"**, which are opposite facts;
- contexts get renamed underneath you;
- an old failing run sits beside a newer green re-run, and only the
  newest per **name** counts.

Two wrong verdicts in one day, and **the direction is the whole point**:

1. STALLED announced on #767 for a SHA transcribed by hand with the tail
   wrong. A nonexistent SHA has no check-runs and nothing in flight,
   which is the literal definition of STALLED — so the rules answered
   **correctly about a thing that does not exist**. The real head had
   seven runs with Integration still going.
2. The fix guarded on `[ -n "$SHA" ]`. The 4xx body walked straight past
   it, because an error body is not empty.

**Both bugs made the tool more confident, not less, and both were in the
merge direction. Adding rules is what produced both.** A tool whose
failure mode is louder certainty is not a thing to gate on, however many
rules it accumulates.

**So "what would it have to prove before we can gate on it" is the wrong
question.** It should live in `scripts/` — every rule in it was learned
by somebody being confidently wrong first, and that knowledge currently
dies with a session — but as an **advisory** tool. Its job is to make the
queue cheaper: point a reviewer at where to look, and **refuse when it
cannot tell**. Refusal is the only behaviour that fails safe, so what it
must prove is that its **refusals** are correct, not that its greens are:

- every refusal arm driven by a test — unresolvable SHA, unresolvable
  PR, unreadable branch protection, an empty required set, `gh` absent
  or unauthenticated, a rate-limited 403;
- **recorded fixtures, not live calls**, so a GitHub outage cannot turn
  the meta-test red and the four traps above become pinned artefacts
  rather than anecdotes;
- a **vacuity refusal** — examined zero contexts must say so, never
  report all-green. Item 1's floor, in this gate's own terms;
- the three verdicts rehearsed in all three directions on real SHAs;
- **a refusal must be distinguishable at the EXIT CODE**, not only in
  prose. "Cannot judge" sharing an exit code with "not yet done" is how
  a wrapper turns a refusal back into an answer.

Two reusable pieces come out of it. The small one: **guard on shape, not
emptiness** — `^[0-9a-f]{40}$`. The large one: **resolve, never
transcribe**, which has since generalised twice more, most recently into
rule 6a and item 13 — a CLEAR against a head that has moved is
indistinguishable from a CLEAR.

**If we want a gate in this direction, it is the CLEAR itself**: a human
verdict against a named SHA, which rule 6a makes mechanically checkable.

Filed shape: `scripts/ci-verdict.sh` + `scripts/test-ci-verdict.sh`
(neither exists on `dev` today), v1.9.0, **advisory**, not started.

## 15. A `-run` filter silently narrows the OBSERVER set

**master-release's, measured on their `mountPrep` branch; routed through
client1.**

Four mutants against the shape gate. Bare `mount`, bare `mkdir` and a
relative `bin/mount` all died. The fourth — repointing `mountBin` to
`/usr/bin/mount`, **absolute but not what the image contains** —
*appeared to survive*, and died the moment the run stopped being scoped
to `-run TestMountPrep` and the whole package was allowed to speak. What
killed it was the Dockerfile parity test, in both directions of its set
comparison.

> **A mutant that "survives" can be an artifact of how the tests were
> invoked rather than a gap in coverage.** Scope a mutation run to one
> test only when the claim is "*this test* kills it". For "*nothing*
> catches this", the run must be package-wide, or the conclusion is
> about the filter and not about the code.

Same family as item 1: the measurement ran, but not over what the
conclusion was about.

**The inverse control, adopted as the standard form:** a mutation table
is evidence only if the same harness has been shown to report
**SURVIVAL** against a test that genuinely cannot see the defect. On
#766 the 24 double-`Load` mutants report 24 dead against the new
concurrency test and **24 survived** against
`TestMetrics_GoldenExposition`. Without that second run, "24/24 killed"
and "the harness silently did nothing 24 times" are the same output.

That control belongs in the runbook beside item 1's two, because it is
the one that makes a mutation table mean anything at all.

## 16. The floor rule as a declaration gate, with shrinkage as the
primary half

**client1's design, answering master-release's question of which habits
deserve a gate. The answer was: this one only.**

*Assert over the whole rendered surface* is **not** gateable — a gate
cannot derive what the surface **is**, and where it applies here it is
already a mechanism rather than advice
(`TestMetrics_EveryHealthFieldIsExposed` walks `HealthResponse` by
reflection and fails on a field nobody claimed). Generalising it means
inventing a coverage notion per test, which is how you get a gate that
waves everything through.

The floor rule, **as a declaration rather than a static analyser** —
inferring "this loop is the assertion" from shell or Go source is the
fuzzy pattern-matching that produced `check-version-pins` matching only
well-formed pins:

> Every `scripts/check-*.sh` prints `INSPECTED <n> <noun>` before any
> clean verdict, and a manifest records each script's floor. The gate
> checks two mechanical things: every check script has an entry and
> emits the line, and no script's count is below its declared floor.
> **The gate cannot know what a script should have inspected. The author
> can. Force them to say it, then hold them to it.**

Three constraints, each from something that actually bit us:

1. **A declared floor of 0 or 1 is rejected outright.** Otherwise the
   declaration satisfies the gate and proves nothing — waiver-by-reflex
   in a new costume.
2. **The floor catches shrinkage, not just zero, and shrinkage is the
   primary mechanism.** A floor catches the measurement that never ran —
   client1's golden extraction, 0 of 56. **Shrinkage** catches the check
   that was correct, and narrow, and had quietly stopped covering its
   subject — master-release's parity test filtering three elements down
   to one, which would sail through a floor of 1 while guaranteeing one
   of three paths. A bare `> 0` cannot see that at all.
3. **It ships with `scripts/test-check-floor-declared.sh` proving both
   verdicts**, or it is precisely the class of thing it exists to catch.

The Go-side variant: a helper `assertInspected(t, got, floor, noun)`,
required in any test function containing a range loop with
`t.Error`/`t.Fatal` in its body. Greppable per function, and cheap enough
that requiring it universally beats introducing a waiver.

**Three people invented this rule independently in one day** — client1 on
the golden extraction, and this ledger twice, refusing to report below 30
atomics and below 200 extracted lines. That is the argument for it
belonging in the corpus rather than in everyone's judgement. Item 1
measures the ground it has to cover: eight of fifty-six gates refuse
today.

## 17. A stale claim can be one bullet away from the text that corrects it

`docs/internals.md` also said *"The snapshot is not a single atomic
instant, and that is deliberate"* — in the bullet **immediately above**
the one flagged in item 12. That sentence is **true** of a counter read
on its own, and it is exactly the reasoning that licenses #730 the moment
a rendered value is **combined** from two of them. Left standing, the
internals document would have justified the defect one bullet above its
own correction.

**No grep run that day would have found it** — not client1's, not
oversight's — because it contains neither the symbol nor the claim. It
was found by asking what the *neighbouring* text now implies.

master-release's note on it is worth quoting rather than paraphrasing:

> *"I do not know how to make that a rule, which is why I want it said
> plainly: that is the part of review that does not reduce to a
> pattern."*

**The work, such as it is:** nothing gateable. What it earns is a line in
the runbook saying that after a mechanical sweep, the text **around**
each hit gets read — because a claim that survives is more often adjacent
to the one that was corrected than identical to it.

## 18. The golden fixture numbers fields by INDEX, so every field-adding
PR collides with every other one

**client1's, with three instances from a single day as its evidence.**

`fixtureSnapshot` numbers every `HealthResponse` field **by position**.
Adding a field shifts the value of every field below it and rewrites ~40
golden lines that have nothing to do with the change. Both consequences
were seen, repeatedly:

- **Any two PRs that add a `HealthResponse` field conflict, serially,
  forever.** Three collisions in one day; #766 was sitting on one, and
  #769 (#731) adds counters and hits it next.
- **The real signal drowns.** In #766, 48 golden lines move and **only
  six of them changed meaning**. The other 42 are pure index arithmetic.
  A reviewer who does not do the delta analysis cannot tell those apart —
  and "cannot tell those apart" is the same condition as not reviewing
  it.

**Fix: number by field NAME rather than position** — a stable hash of the
json tag, or an explicit per-field table. Two PRs adding different fields
would then never touch the same lines, and a changed line would mean a
changed *value*.

Worth stating what it does **not** fix, because the neighbouring item is
the bigger one: it removes the collision, not the interaction. #757 and
#761 had no shared file at all (item 7), and no renumbering scheme would
have brought them into contact.

**The practice that goes with it, and it earned its place three times in
one day:** resolve a generated file by **regenerating**, never by taking
a side — taking a side is a hand-written expectation wearing a generated
file's clothes. Then **write down the churn you predict before you
diff**. client1 predicted `{-80:1, -60:1, -40:1, -30:3, +60:42}` on the
last rebase and measured exactly that. A prediction that matches is
evidence; one that misses by a line is a question worth asking — last
time the extra line was #764's new counter, and finding out *why* is what
made the exercise evidence rather than noise.

## 19. A count beside a list is a second copy that can disagree with it

Measured on this release's own notes. `RELEASE_NOTES.md` said "fifteen
new health counters" in three places. The number went false about a
minute after the section was frozen for review, when #767 merged
`conflict_probe_stale_addrs` — a PR the section had nothing to do with.

The structural property is the finding: **that section asserts facts that
are functions of what has merged, and it merges last.** A verdict on it
is valid only until the next merge, *including* a verdict given
correctly, driven, at a frozen head. No amount of review discipline
closes that.

The fix was to delete the number rather than correct it, and let the
table be the count. **Deleting the second copy deletes the failure mode**
— the same move as storing the `*_v4` fields rather than deriving them.

And the interesting half: **removing the number exposed the list being
wrong.** Making the table authoritative forced it to actually *be* the
set, and it was not — 14 rows against 16 counters, with
`tombstone_quarantines` named only in prose. The number and the list had
already disagreed *before* #767 merged, and nobody could see it, because
the number was doing the reader's counting for them.

> A count beside a list has a shelf life. A list does not. Where a
> document states a count, a merge state, or anything else a later merge
> can falsify, prefer the list, the table, or the link.
